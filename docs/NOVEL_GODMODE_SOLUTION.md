# 小说神作模式问题总解决方案

## 1. 问题诊断

当前“神作模式”已经具备较强的规则框架，但仍存在 8 类核心问题。如果不先解决这些问题，再继续加点子、加轮数、加文件，系统只会越来越重，而不会越来越强。

### 1.1 Prompt 过载

现象：
- `NOVEL_GODMODE_MASTER_PROMPT.md` 很完整，但信息量极大。
- 如果运行时直接把整份母本持续喂给模型，模型很容易前面记规则、后面忘素材，或者前面看素材、后面稀释规则。

代价：
- 输出会漂。
- 讨论会重复。
- 模型会为了“覆盖所有要求”而产生低密度总结，而不是高强度推进。

### 1.2 点子库过密但不收敛

现象：
- 原始点子库很强，但总量极大。
- 如果没有稳定的分层和筛选机制，AI 会倾向于“都想要一点”。

代价：
- 大点子不够统治全局。
- 中小点子虽然多，但缺少挂靠关系。
- 最终会变成“点子清单作品”，而不是“因果严密的群像智斗史诗”。

### 1.3 阶段内跑题

现象：
- 现在已经区分了“阶段 / 轮 / 回合”，但一个阶段内部仍可能同时讨论太多事情。
- 例如设计“五大核心事件”时，AI 往往会顺手把终局、人物弧线、章节细纲一起提前展开。

代价：
- 当前阶段的唯一问题被稀释。
- 轮数看起来很多，实则推进效率不高。

### 1.4 AI 偷跑阶段

现象：
- 即使 prompt 已经明确“本轮不做什么”，AI 仍可能提前进入收尾、提前定终局、提前给下一阶段下结论。

代价：
- 讨论强度下降。
- 十几轮后就开始主持人确认与总结。
- 真正需要高强度打磨的中期阶段被提前收缩。

### 1.5 高字数低质量

现象：
- 字数和标题数门槛可以逼出更多文本，但不能自动逼出更强的桥段、伏笔、人物推进和诡计结构。

代价：
- 交付看起来很长，但不一定更狠。
- 容易出现“写得多，但记忆点不够”的问题。

### 1.6 主持人负担过重

现象：
- 当前系统仍容易把大部分整合与最终写稿压力压到 Host 身上。

代价：
- 其他席位更多在讨论，Host 在后期疲于汇总。
- 效率低。
- 容易出现“中后期主要是主持人输出”的单点瓶颈。

### 1.7 默认策略与重型策略混用风险

现象：
- 项目已经把默认 workflow 收回通用模板，但神作模式 preset 与重型 seed 仍然存在。
- 如果后续不把“默认能力”和“重型配置”继续分清，很容易再次把通用能力做成特定题材绑定。

代价：
- 普通辩论会被重型规则拖累。
- 高强度创作方案也会因为通用性要求被迫妥协。

### 1.8 缺少运行时精简版 Prompt

现象：
- 目前有母本 prompt，也有 workflow 配置，但缺一份真正为运行时设计的“精简执行版 prompt”。

代价：
- 运行时只能在“全量母本”和“过度简化”之间摇摆。
- 模型无法稳定聚焦当前阶段、当前轮次、当前子任务。

## 2. 总方案：三层控制架构

最佳方案不是继续往一份 prompt 里叠规则，而是把系统拆成三层，各司其职。

### 2.1 MASTER Prompt：总控母本

职责：
- 定义创作哲学。
- 定义阶段规则。
- 定义点子分层规则。
- 保留完整素材库。

不负责：
- 每轮都直接下发给模型。
- 直接承担运行时精确执行。

原则：
- 它是“上位规则与素材库”。
- 它负责定义标准，不负责每轮执行。

现有对应资源：
- `docs/NOVEL_GODMODE_MASTER_PROMPT.md`

### 2.2 Runtime Prompt：运行时精简版

职责：
- 只服务当前阶段、当前轮次、当前子任务。
- 只保留当前轮真正需要的约束。
- 明确本轮该做什么，不该做什么。

必须只保留这些信息：
- 当前阶段
- 当前轮次
- 当前子任务
- 本轮禁止做什么
- 本轮输出格式
- 本轮要更新哪些文件

不负责：
- 携带完整素材库
- 携带全书所有规则细节

原则：
- 它是“执行用 prompt”，不是“母本 prompt 的缩写版”。
- 它必须短、硬、聚焦。

### 2.3 Workflow Preset：机器规则层

职责：
- 控制最少轮数
- 控制输出预算
- 控制交付门槛
- 控制阶段切换
- 控制完成条件

不负责：
- 解释创作哲学
- 代替 prompt 做文学判断

原则：
- 它只负责“机器可执行的硬规则”。
- 不把创作说明文塞进 workflow。

现有对应资源：
- 默认 workflow
- `docs/NOVEL_GODMODE_WORKFLOW.json`

### 2.4 三层之间的关系

正确关系应该是：
- MASTER Prompt 定规则与素材边界
- Runtime Prompt 负责每轮执行
- Workflow Preset 负责机器卡口

错误关系是：
- 用一份超长 prompt 同时承担三层职责

## 3. 执行机制

### 3.1 阶段内子任务模板

仅有“阶段”还不够，每个阶段还必须拆成固定子任务序列，避免阶段内跑题。

建议规则：
- 每个大阶段只解决一个核心问题
- 每个大阶段再拆成 3 到 6 个固定子任务
- 运行时每轮只推进当前子任务
- 子任务未完成前，不允许切换到下一个子任务

示例：第 5 阶段“五大核心事件”应拆成：
- 5.1 事件主题与目标
- 5.2 事件对立双方与局势图
- 5.3 事件的大点子 / 中点子 / 小点子
- 5.4 事件误导与反制
- 5.5 事件代价与余波

这样做的目的不是增加流程复杂度，而是防止模型一轮里同时讨论五件事。

### 3.2 运行时压缩策略

MASTER Prompt 不再直接全量喂给模型。

运行时应采用“阶段裁剪 + 子任务裁剪 + 素材按需注入”：
- 只注入当前阶段需要的创作规则
- 只注入当前子任务需要的输出要求
- 原始点子库只按阶段按需引用
- 与当前阶段无关的素材不进入本轮 prompt

推荐原则：
- 不让模型每轮重新消化整套创作哲学
- 不让模型每轮重复看到整份素材库
- 不让模型为“记住全部要求”而牺牲当前推进质量

### 3.3 当前坐标强制机制

每轮输出必须先写“当前坐标”。

至少包含：
- 当前阶段
- 当前轮次
- 当前子任务
- 本轮只推进什么
- 本轮不解决什么

作用：
- 防止混淆阶段与轮次
- 防止模型越级处理问题
- 强迫模型先定位，再发言

### 3.4 阶段切换双重控制

阶段切换不能只靠 prompt，必须由 prompt 与 workflow/runtime 双重控制。

需要同时满足：
- 当前阶段最少轮数已达成
- 当前阶段必要交付已完成
- 当前阶段子任务序列已完成
- 当前阶段质量审判通过

否则：
- 不允许进入下一阶段
- 不允许进入收尾语气
- 不允许把局部共识当作阶段完成

### 3.5 角色分工写作策略

Host 不应再承担全部写作。

推荐分工：
- Host：仲裁、收敛、整合、定结论
- 其他席位：
  - 角色库初稿
  - 事件库初稿
  - 伏笔库初稿
  - 分卷结构初稿
  - 章节扩写初稿

原则：
- Host 负责最终统一口径
- 其他席位负责持续产出素材
- 不让后期变成“六个人讨论，一个人写稿”

### 3.6 质量闸门升级

质量闸门不能再只看：
- 字数
- 标题数
- 是否存在文件

必须升级为多维检查：
- 结构完整度
- 关键覆盖度
- 事件密度
- 角色推进
- 伏笔埋点与回收
- 终局关联

建议后续新增质量检查维度：
- 关键事件至少包含多少有效中点子与小点子
- 人物档案是否具备能力、软肋、执念、命运
- 分卷结构是否具备主题、高潮、悬念
- 章节细纲是否同时具备目标、冲突、转折、结果、钩子、伏笔、人物推进

### 3.7 质量审判机制

每个阶段结束时，必须强制输出“审判”结果，而不是只做总结。

必须回答：
- 当前最强的一笔是什么
- 当前最弱的一笔是什么
- 哪个部分仍然平庸
- 哪个部分如果现在出版最容易被骂
- 哪一项不过关就必须继续打磨

作用：
- 把“完成”改成“通过审判”
- 让系统默认不放行平庸内容

### 3.8 完成条件升级

最终完成不能只靠：
- 达成共识
- 文件写完
- 字数达标

必须同时满足：
- 阶段轮数达标
- 必交文件完成
- 结构检查通过
- 关键事件质量达标
- 伏笔闭环达标
- 终局关联达标

否则只算“阶段性产出”，不算真正完成。

## 4. 推荐配置

### 4.1 Generic

适用场景：
- 普通辩论
- 中短篇创作
- 一般方案设计

特点：
- 轮数适中
- 文件较少
- 门槛较轻
- 重视通用性

原则：
- 默认工作流继续保持这一档
- 不把神作模式要求直接塞入默认配置

### 4.2 Balanced

适用场景：
- 长篇小说预研
- 高质量群像创作
- 需要更强过程控制，但不追求极端重型

特点：
- 增加阶段最少轮数
- 提高交付厚度
- 使用 Runtime Prompt 精简版
- 引入阶段子任务

原则：
- 适合作为“高级创作模式”
- 在强度和通用性之间平衡

### 4.3 Extreme

适用场景：
- 百万字级神作圣经
- 群像智斗史诗
- 长周期高密度创作

特点：
- 长轮次
- 多文件
- 重质量闸门
- 强分工写作
- 强审判机制

原则：
- 只作为独立 preset 使用
- 不回灌到默认 workflow

## 5. 与现有接口与配置的关系

本方案不是推翻现有能力，而是在现有能力基础上继续分层。

### 5.1 继续复用的现有能力

继续使用现有 `workflow.json` 已有能力：
- `phaseMachine.phases[].minRounds`
- `promptPolicies.outputBudget`
- `deliverables.requiredFiles`
- `transitionRules.finalization`

这些能力已经足以承载“阶段轮数、输出预算、交付门槛、收尾限制”的硬控制，不需要回退。

### 5.2 推荐后续新增但仍保持通用的配置

建议后续逐步扩展：
- `phaseMachine.phases[].subtasks`
  用于定义阶段内固定子任务序列
- `promptPolicies.runtimePromptMode`
  用于选择运行时 prompt 生成策略
- `deliverables.requiredFiles[].qualityChecks`
  用于定义更细的结构与质量检查
- `roleWritingAssignments`
  用于明确不同席位负责哪些交付文件或初稿区域

原则：
- 新增的是“能力”，不是把神作模式写死成默认值
- 通用性继续保留在能力层
- 题材特化继续放在 preset 层

## 6. 落地顺序

为了避免一次改太多，推荐按以下顺序推进。

### 第一步：补运行时精简版 Prompt

优先级最高。

目标：
- 把 MASTER Prompt 从运行时剥离
- 正式建立 Runtime Prompt 层

产出：
- 一份新的运行时精简 prompt 文档

### 第二步：给每个阶段补子任务模板

目标：
- 防止阶段内跑题
- 让运行时 prompt 真正能聚焦

产出：
- 阶段子任务定义方案

### 第三步：补角色分工写作机制

目标：
- 降低 Host 单点压力
- 提高多席位持续产出效率

产出：
- 文件级写作分工方案

### 第四步：升级质量闸门

目标：
- 从“长”升级到“狠”
- 防止高字数低质量

产出：
- 新的质量检查定义

### 第五步：补 balanced / extreme 双预设

目标：
- 让“高质量模式”和“极端神作模式”可切换
- 保持默认 workflow 通用

产出：
- 预设分层方案

## 7. 验收标准

这份方案是否成功，不看文档写得多不多，而看后续落地后能否达成以下结果：

### 7.1 阶段清晰度

任意一轮输出都能明确区分：
- 当前阶段
- 当前轮次
- 当前子任务
- 本轮不解决什么

且不再频繁越界讨论。

### 7.2 运行时稳定性

模型不再每轮重复消化整份母本 prompt，输出明显更聚焦当前子任务。

### 7.3 讨论强度

第 10 几轮不再过早进入主持人总结与确认，而是真正在中期持续打磨事件、诡计、关系和结构。

### 7.4 写作效率

多席位都能持续产出素材文件，不再主要依赖 Host 一人完成大部分写作。

### 7.5 质量提升

最终交付不只更长，还要表现出：
- 更强事件密度
- 更高伏笔闭环度
- 更强人物辨识度
- 更狠的终局关联

### 7.6 通用性

普通辩论继续可用默认 workflow。
神作模式只在选用对应 preset 时生效。

---

## 8. 结论

最佳解决方案不是继续往一份 prompt 里堆更多要求，而是建立清晰的三层控制架构：
- 用 MASTER Prompt 定义标准与素材边界
- 用 Runtime Prompt 驱动每轮执行
- 用 Workflow Preset 提供机器硬约束

同时再补上：
- 阶段内子任务
- 角色分工写作
- 质量审判机制
- 完成条件升级

只有这样，系统才会从“高野心提示词”进化成“真正可执行的神作工厂”。
